# Function bodies that are the same code twice, and why each one is allowed.
#
# Written by ci/duplicate-bodies.py --bless and edited by hand: blessing records
# the pair, and a person writes what makes it not a copy. A pair whose reason is
# 'generated' or 'trivial' is usually a pair that should have been extracted.
#
# format: <file::fn>|<file::fn>|<why this is two functions and not one>

crates/ferrosys-cli/src/args.rs::detect|crates/ferrosys-cli/src/args.rs::identity|two subcommand parsers over the same argument vocabulary, which every verb reading an image shares: `identity` gained `--offset`, the option every image-reading verb takes, and with it the same token loop. What each accepts beyond the shared vocabulary — a rewrite's three fields against a classifier's none — is the body, and each parser naming its own flags is what keeps a flag added to one a decision rather than an inheritance
crates/ferrosys-lzfse/src/lib.rs::sweep_changes_of|crates/ferrosys/src/compress.rs::sweep_changes_of|the property every decoder is held to, a stream changed a byte at a time and cut at every length, in the two crates that hold decoders. `ferrosys-lzfse` is a crate `ferrosys` depends on and cannot depend on `ferrosys` in turn, and the helper is a test's, part of neither crate's surface, so each crate's tests carry it for the decoders that crate holds
crates/ferrosys/src/apfs/fs.rs::list|crates/ferrosys/src/btrfs/fs.rs::list|a directory's names, resolved to nodes, in two families whose entries name a node differently. What a listing hands back is already one function, `tree::listed`, which both pass their names through; what is left is each family's step from an entry to its node, and that is the body. A btrfs entry carries a key that may be a subvolume's root, so it is stepped through `step`, which crosses into the subvolume as a walk does; an APFS entry carries an inode number, resolved and then held to recording this directory as its parent, as an APFS walk holds it. A shared listing would take that step as a parameter, which is the body restated with its one difference as a hole
crates/ferrosys/src/apfs/fs.rs::walk_tree|crates/ferrosys/src/btrfs/fs.rs::walk_tree|the shared walk projected into the shared frame, with each family's hard-link identity: the projection of a node to its kind is already one function per family, and what remains is which nodes are two names for one. A btrfs node is a subvolume and an inode together, since inode numbers start again in every subvolume, so its identities are keyed by the pair; an APFS inode number names one node in its volume, and its link count is read through the record that holds it. A shared walk would take the key and the count as parameters, which is the body restated with its two differences as holes
crates/ferrosys/src/exfat/model.rs::node_for|crates/ferrosys/src/fat/model.rs::node_for|the same, one step further in: what a source entry *becomes* in each family's model. Both dispatch the same five arms over `EntryKind` because both families lose the same kinds, and both write a hard link as a second copy — but what each constructs is that family's own `Node`, holding a run of clusters sized in that family's own units. The dispatch without the construction is four lines
crates/ferrosys/src/exfat/model.rs::place|crates/ferrosys/src/fat/model.rs::place|the spine that walks one entry into the tree, whose steps are shared and whose order is the load-bearing part: a kind the format cannot hold is decided before the name is, so an absent entry's name is never refused over. What differs is the attribute word each family builds and where a directory's own times go — exFAT records them in the entry naming the directory, FAT in the `.` entry inside it — and neither is expressible without naming the family's types
crates/ferrosys/src/exfat/name.rs::place|crates/ferrosys/src/fat/name.rs::long_name_units|two validations of one shape that reach the same limit by different arithmetic. The character rule is already shared, in `path::is_reserved_name_char`; what remains is a decode, an emptiness check, a trailing-dot check, and a bound — and the bound is 255 units in both families for unrelated reasons: exFAT's is the width of the `NameLength` byte, FAT's is what twenty long-name entries of thirteen units reach. A shared function would take the limit as a parameter, at which point it is "validate a UTF-16 name against a limit" and the two constants are the whole of what it says
crates/ferrosys/src/exfat/read.rs::chain_cluster|crates/ferrosys/src/fat/read.rs::cluster_at|walking to the nth cluster of a chain, in two families whose allocation tables are not the same table. What is shared is the resume cursor and the loop, and what differs is underneath both: a FAT entry is twelve, sixteen, or thirty-two bits and its end-of-chain mark is a band per width, where an exFAT entry is thirty-two bits and one value ends a chain. The exFAT reader also has a *second* run shape this function is not reached for at all — a stream declaring `NoFatChain` is arithmetic — so the shared step is `stream_cluster`'s, one level up, and that one has no FAT counterpart because FAT has no such flag
crates/ferrosys/src/fat/materialize.rs::the_streamed_image_is_the_in_memory_image|crates/ferrosys/src/fat/materialize.rs::a_populated_format_is_reproducible_and_streams_the_same_bytes|two tests over one fixture, asserting different properties of it: that streaming and buffering agree, and that two formats of the same tree are byte-identical. The setup is shared because it is the same volume; the assertions are the point and they are different
crates/ferrosys/src/read.rs::a_directory_entry_naming_an_inode_that_does_not_exist_is_refused|crates/ferrosys/src/read.rs::a_directory_entry_carrying_a_name_no_directory_can_hold_is_refused|the two faults `read_dir` refuses at the same point in the same crafted directory — a reference out of range and a name no directory can hold — asserted separately because a reader that caught one and not the other would pass a merged test
crates/ferrosys/src/read.rs::scan_files_an_out_of_range_extent_against_the_extent_tree|crates/ferrosys/src/read.rs::scan_files_an_out_of_range_xattr_block_against_the_attribute_block|the same corruption applied to two different structures, each checked to be filed under its own subsystem. Sharing the body would mean parameterizing over the byte offset to damage, which is the one thing each test exists to state
crates/ferrosys/src/btrfs/fit.rs::a_fitted_size_formats_and_one_sector_less_does_not|crates/ferrosys/src/exfat/fit.rs::a_fitted_size_formats_and_one_sector_less_does_not|the same claim, that a fitted size formats and a sector less does not, held against two families whose plans, options and readers share no type: `btrfs::FormatPlan` and `exfat::FormatPlan` are separate types with no trait between them, and the readers walk differently, the btrfs walk counting its root. A shared helper would be generic over a trait that exists only for these two tests, which is the body restated with its type parameters as holes
